# v13.1.0 研究与设计：让云端真正做构图 + BYOK 可用性诚实化

> 口径：本项目为多轮公开资料学习后全部自研的单文件 PWA。本文只记录**可核查依据**、
> **实测数据**与**由此推导出的实现决策**；未核实的推测一律标注。

## 0. 这一版要解决的两个真问题

1. **云端构图被本地候选封顶**。v13.0.0 的"真 AI 构图"实际是让云端在 A/B/C/原图里四选一，
   而 A/B/C 里 B/C 只是**画幅转换**（裁切中心仍是本地像素质心）→ 云端在做"选画幅"，不是"找最美区域"。
2. **BYOK"测试通过、真跑超时"**。体检只发 64×64 小图 + `max_tokens:5` 且只看 HTTP 200，
   正式请求是 896 联系表 + 500 token + 默认开思考 → 两者根本不是同一条链路。

## 1. 现场实测（共享代理 · glm-5.3-flash · 真实 896 联系表 116,565 B / base64 155,420 / prompt 1,353 token）

| 请求配置 | HTTP | 用时 | content | finish_reason | reasoning token |
|---|---|---|---|---|---|
| 不传思考参数（重复 3 次） | 200 | 17.0 / 19.6 / 0.6s | **0 字** | length | 498–499 / 500 |
| `thinking:{type:"disabled"}` | 200 | 15.1s | 286 字合法 JSON | stop | 0 |
| `reasoning_effort:"low"` | 200 | 8.3 / 7.3s | 合法 JSON | stop | 0 |

64×64 体检侧对照：不传思考参数 → 200 / 6.8s / **content 空**（旧体检仍会显示"✅ 可用"）；
关思考 → 200 / 7.5s / "OK"；用真实尺寸图片关思考 → 27.9s（>旧体检 20s 上限 → 假阴性）。

**结论**：思考开关决定云端可用与否；旧体检同时存在假阳性与假阴性。

## 2. "构图像魔法"类爆款的量化分析（逐帧测量）

对象：抖音「菠萝小聂」`7669291171814902143`（12 秒，4 例，2026-08-02 发布，3.2 万赞）。
页面文案/评论通过真实浏览器读取；帧通过 ffmpeg 抽取，取景框用像素检测测量。

| 例子 | 框宽高比 | 占画面宽 | 占画面高 | 保留面积 | 等效变焦 |
|---|---|---|---|---|---|
| 湖边两树夹长椅 | 0.669（2:3） | 29.4% | 32.6% | **9.6%** | 3.2x |
| 共享单车 + 水洼倒影 | 0.669 | 31.4% | 34.4% | **10.8%** | 3.0x |
| 天桥下花丛夜景 | 0.669 | 33.5% | 36.4% | **12.2%** | 2.9x |
| 落日剪影（网格间距反推） | ≈0.669 | ≈37.5% | ≈43% | **≈16%** | 2.5x |

对照 v13.0.0 闸门（单边≤15%、四边≤40%、保留≥72~78%）≈ **1.2~1.5x**：差一倍以上。
成品帧细节明显比原广角更密（EXIF 叠加），说明作者是**走近/用 2x-3x 长焦重拍**那个局部，
不是把那一张广角裁 10% → "魔法"里约一半必须在拍摄时兑现。

评论印证（原文）："懂了，随便拍，然后截图"、"所以新手买哈苏，拍完再构图"、
"后来才发现这是摄影眼…现在有的手机已经有这个功能了，自动构图提示…未来逃脱不了AI"。

## 3. 大裁的像素授权（为什么不能无脑放开）

`z = 1/√保留面积`。要求输出短边≥900、长边≥1350（朋友圈官方短边≤1080、Instagram 4:5 长边 1080、
iPhone 17 Pro 全屏 2622×1206）时：

| 源 | 最大安全等效变焦 | 对应保留面积下限 |
|---|---|---|
| 12MP | ≈2.4x | ≥16%（本工具取 25% 起步） |
| 24MP | ≈3.5x | ≥8% |
| 48MP | ≈5.6x | ≥3% |

行业佐证：Apple 官方把"48MP 传感器中心 12MP 裁切"命名为 **optical-quality 2x**（=保留 25% 面积）；
Nikon 官方规格表把 DX/1.3x 裁切当正常档位；Canon R50 有官方 2x/4x Digital Teleconverter。
反例约束：Google 官方明确"放大不改变视差、裁切无法展示框外内容"→ 广角透视裁完仍是广角透视。

## 4. 学术依据与诚实修正

**支持本方案**
- Set-of-Mark（arXiv 2310.11441）原文逐字："GPT-4V can hardly produce a sequence of accurate
  coordinates…" → **让模型选编号/离散档位，不让它报坐标**。
- Q-Align（**ICML 2024**，非 NeurIPS 2023）离散等级优于分数回归（+10% 消融）→ 支持"每边 0/5/10/15/20/25 档"。
- Cropper（CVPR 2025 / arXiv 2408.07790，Google 系）：示例检索 + 迭代细化，输出归一化坐标；
  可引用范围仅限"VLM 出框 + 多候选 + 迭代"是可行路线，**不能**引用它证明"单次裸报坐标不行"（未读到量化消融）。
- GroundingME（arXiv 2512.17495）：最佳模型 45.1%（Accuracy@0.5）、多数模型拒识 0% → 任务是语言指代定位，
  **不可**换算成构图裁切成功率；可取的只有"必须留 reject 通道"。
- Twitter 裁切研究（PACM HCI CSCW3，DOI 10.1145/3512930；常被误记为 FAccT 2022）：官方结论是
  "公平性指标不足以刻画代表性伤害，应移除显著性自动裁切、把选择权交还用户" → 我们要求
  **并排预览 + 一键还原 + 多主体禁止挑最好看的脸**。

**必须修正的旧说法**
- 三分法**没有**强实证背书：Amirshahi 等（Art & Perception 2014, DOI 10.1163/22134913-00002024）原文
  "the rule seems to play only a minor, if any, role in large sets of high-quality photographs and paintings"；
  McManus 2011 亦未支持 Arnheim 重心说。→ 九宫格只作为**用户熟悉的取景辅助**，不得宣传为"被实证的美学定律"，
  也不承诺"AI 美学打分"。
- PICD（CVPR 2025）"MLLM 构图区分≈随机 0.33"仅见于作者自撰推广文，一手 PDF 未核实 → 不作为定论引用。
- Datta 2006 特征清单未能逐条对到原文（Springer 付费墙）→ 不写"特征体系源自 Datta"。
- 各家思考参数**不能按模型名前缀猜**：腾讯云文档称 GLM-5.3 不支持 `disabled`，而我们在共享代理实测
  `glm-5.3-flash` 接受 `thinking:{type:"disabled"}`；Kimi K3/K3.1 只能思考（关思考 400）；
  MiniMax M3.1-Flash 关思考返回错误码 2013；DeepSeek `deepseek-flash` 默认 thinking=enabled 可关；
  通义 Qwen3.7/3.8 默认开思考、`qwen3-vl-plus/flash` 默认关。→ 改为"厂商+模型"查表 + 400 降级重试。

## 5. v13.1.0 实现清单

**构图上限**
- 新增 `_cropBudget(a,scene)`：按源真实像素 + 场景 + 暗/糊证据给出 `minArea/tightArea/maxZoom`。
- 新增 `_intentCandidates`：三分左/右、地平线上/下、小框重构图、小框+三分、去死边、画幅 —— 空间意图真正不同。
- 新增 `_validateNewCrop`：统一硬校验（面积预算、单边/四边分级上限、主体证据、肤色边缘、人物 3% 边距、
  多主体拒大裁、`_objectGuard`、`_cropQualityScore`）。
- `_cropQualityScore` 面积项改为预算感知（旧版偏好"保留 85%"，是"不敢裁"的数学根源）。
- `_buildCompositionCandidates` 输出 ≤8 个真实裁切 + 原图，近似重复用 `_cropsSimilar` 剔除。
- `_cropBudget` 人物分支按**人物框占画面面积**分档：≥10% 保守（`minArea=0.40`、禁小框）/ <10% 允许主动重构图
  （`minArea=0.30`、放开小框），`_intentCandidates` 三处闸门同步由 `!pb` 改为 `!pbBig`。
  人物安全不再依赖"不生成候选"，而由 `_validateNewCrop` 的人物 3% 边距 + `_objectGuard` + `_skinEdgeGuard` +
  多主体拒大裁保证（与本组 122/70 张重跑逐行 diff 为 0 互为印证：这是防御性修正，不是本组瓶颈）。
- 四边合计 ≤5% 的微裁在"像素方案"与"提交方案"两处一律归零。

**云端**
- 联系表自适应 2×2（≤4）/3×3（5~9，每格 384px）。
- 协议扩展：`action=select|refine|reject`、`base`、`trim{l,t,r,b}∈{0,5,10,15,20,25}`、`guard`、`confidence`、`reason`。
- 坐标全部本地算；refine 不过校验就退回原候选并如实说明；reject 时用原图。
- 新增失败原因 `thinking`（200 但 content 被思考 token 吃光）与 `format`（不按 JSON 回），文案不再笼统"网络问题"。
- 可观测性：`state._cloudPickRaw` 保留模型指令形态（`hasActionKey/action/base/trim`），经
  `__ai.cloudPickRaw` 暴露；`__ai.plan` 增加 `aiRefined/aiRejected/aiGuardWhy`。
  配套 `tools/probe-cloud-actions.js`（触发率与"云端返回后候选条是否还在"）与
  `tools/summarize-cloud.js`（把云端日志压成指标，优先读字段、旧日志才退回文案匹配）。
- 状态文案分两种原因：云端方案被本地硬校验否决 ≠ 云端建议不裁而本地已裁得更紧。

**BYOK**
- `_thinkModeOf(vendor,model)` + `_cloudThinkParams` + `_cloudHeaders` + `_cloudSend`（400 自动去参数重试一次）。
- 体检改为两档真实链路：① 小图视觉（断言 content 非空、finish≠length）② 896 合成联系表 + 严格 JSON
  （断言可解析、必需字段、耗时），结果分档显示；换厂商/模型/Key 立即清空。
- 删除 `qwen3.5-flash` / `deepseek-chat` 死兜底；SCF 地址从 6 处硬编码收敛为 1 个常量。
- 时钟统一：60s 硬截止从**云端请求真正发出**开始计（旧版从点击算，本地模型预检会吃掉预算）。
- 预设元数据：非思考/自动关思考/只能思考（慢）标注 + 把"只能思考"的模型移出默认推荐位。

**P1 修复（外部审计）**
- 小人物未被模型检出 → `skinGrid` + `_skinEdgeGuard`（裁切带内出现成块肤色即否决）。
- 低质/无主体/占位图被强裁 → `_subjectEvidence` 接入 `_proactiveComposition` 与候选校验。
- 暗调美食误推夜景滤镜 → `hasFoodEvidence` + 暖色不在天空带时才判食物，夜景/冷调滤镜负分。

## 6. 测试数据诚实化（重要更正）

- 旧版 README/发布说明写"本地 100 张 / 云端 50 张真实拍摄图"。md5 实测：`imgs/test100` 只有
  **70 个唯一图**、`imgs/test50` 只有 **42 个唯一图**，全库唯一图 **79** 张；其中含 12KB 级的
  **emoji/占位图**（`night_11.jpg` 与 `street_6.jpg` 字节相同，实际是一枚爱心表情），
  且全部为 800px 宽的网络缩略图。**"100 张真实拍摄"的说法不成立，本文与发布说明予以更正。**
- 附带收益：重复图给了一个免费的确定性证明——9 组字节相同的图，回归结果 100% 一致。
- 新做法：`tools/fetch-picsum.js` 抓取 Unsplash 授权真实照片（含作者/原始页面/尺寸/许可，记录在
  `tests/data/picsum-manifest.json`），`tools/label-commons.js` 用独立 VLM 打标签（场景/是否照片/人数），
  回归脚本加 md5 唯一性断言与"非照片图"负例（断言不裁切）。
- 局限（诚实说明）：本机访问 Wikimedia Commons 超时，Picsum 无法按类目挑选，因此类目分布不均衡；
  最终验收仍建议由用户投入自己的手机实拍图（含 24/48MP 高像素原图）跑一轮。

## 7. 实现过程中被实测推翻的六个设计假设（诚实记录）

这六条都是"单测通过、浏览器里不生效""闸门过严导致能力归零"或"测量本身失真"类型的坑，只有用真实图片跑真实链路才暴露：

1. **本应用的工作分辨率把"魔法框"幅度封顶了。** 上传时 `maxSide=2400`（本版按设备内存分档：
   `navigator.deviceMemory>=4` 时 3200，iOS 无该 API 保持 2400）。裁切是从这张工作图里裁的，
   所以再高的原图也只有 2400/3200px 可用：2400×1800 的极限约 **1.78x**、3200×2400 约 **2.35x**、
   12MP 工作图约 **2.7x**。抖音创作者能做到 2.5~3.2x 是因为他**用长焦重拍**（光学像素更多），
   不是把那一张广角裁到 10%。→ 结论：`tightArea` 档位必须按"工作图真实像素"标定，
   不能按手机标称像素标定；超过 ~2.7x 的部分属于"拍前引导"的能力范围，不是拍后裁切能兑现的。
2. **肤色边缘守卫第一版把构图能力清零了。** 第一版只看"被裁条带里有没有成块肤色"，
   结果一张"木桌上的笔记本电脑"照片（无任何人物）肤色占比 25.3%，把三分/去死边/画幅候选全部否决。
   木桌、木地板、秋叶、砖墙、暖色外墙都会整片落进 YCbCr 肤色范围。
   → 现在只在两种情况否决：① 皮肤**跨在裁切线上**（跨界带 ≥2 块且保留区也有 ≥2 块）；
   ② 裁掉条带里有 ≥3 块且占全图肤色 ≥60%（把人整个裁掉）。并且加了总闸：
   **全图肤色占比 >18% 判定为大面积暖色表面，直接放行**。
3. **"候选数够不够"必须在浏览器里看，Node 单测看不出来。** 提取式单测是对源码做文本切片，
   即使函数在页面里因作用域/数据差异没生效，单测照样全绿。→ 本版新增 `window.__v131core`
   调试出口与 `tools/debug-candidates.js`，用浏览器里的真实 `aiData` 复算候选，
   并打印每一条被哪道闸门拦下（本次就是靠它定位到上面第 2 条）。
4. **端侧模型一开，候选数就腰斩；其中"人体框一出现就锁死幅度"是可以直接拆掉的一档。**
   同一张照片：模型关时候选 6~7 个，模型开时只剩 3~4 个。第一版 `_cropBudget` 的人物分支不看面积，
   `_intentCandidates` 里三处 `!pb` 闸门也一视同仁——只要检出一个人体框（哪怕是 2% 大小的远景路人），
   幅度立刻锁到"保留 ≥40%、禁止小框重构图"，三分/地平线/小框候选干脆不生成。
   同时 `tools/probe-cloud-actions.js` 显示：模型关时同一个共享模型 7 张里有 3 张主动要求
   `action=refine`（`action/base/trim` 字段在返回 JSON 里一直存在），而 50 张批量回归（模型开）refine 0 次。
   → 本版按**人物占画面面积**分档：≥10% 保守（保留 ≥40%、禁止小框）；<10% 允许主动重构图。
   人物保护不靠"不生成候选"实现，而靠 `_validateNewCrop` 里与幅度无关的四道硬校验：
   人物框任一边 ≥3% 边距、`_objectGuard`、`_skinEdgeGuard`、多主体拒大裁。
   **诚实边界**：这条改动是**防御性修正**，不是本组样本的瓶颈——重跑后 122 张与 70 张的原始日志与改动前
   **逐行 diff 为 0**（本组照片里"占比 <10% 的小人物"极少）。模型开启时候选从 6~7 掉到 3~4 的实测主因是
   `allBoxes` 物体保护与人物 3% 边距这两道硬校验（属于安全设计，故意不放宽），不是这档锁死。
   refine 在默认配置下经探针验证**可以落地**（模型开的 8 张里 1 张：base A `[0,7,0,9]` + trim(t5,b10) →
   `[0,12,0,19]`，`aiRefined:true`），但同一张图重跑又可能变回 select，说明共享模型的触发既低又抖；
   批量命中率以 `tests/logs/v13.1.0_cloud50.txt` 的**字段化实测**为准，不当作已兑现的常规能力。
5. **回归脚本自己也会测错：`refined=false` 其实读的是 `undefined`。** 给 `tools/cloud-regress.js`
   加"指令落地"字段时，`intent:` 那行在三个快照构造器里缩进不同，只补进了第一个；
   云端返回后真正使用的后两个构造器没有 `refined/pick/candCount`，于是 `!!undefined → false`、`cand=0`，
   看上去像"云端一次都没 refine、候选被清空"。用 `tools/probe-cloud-actions.js` 直接读
   `__ai.plan.aiRefined` 与 `__ai.candidates.length` 才确认：候选条在云端返回 3 秒后仍在（数组 3~4、芯片可点），
   refine 也确实能落地。→ 结论：任何"0 次/没有"的度量，先证明**测量路径本身有灵敏度**（这里靠
   同一张已知 refine 过的照片做对照 + 用另一种读法交叉验证），再写进结论。
6. **我把云端日志里的 `cand=0` 一股脑归因给"候选条被收起"，其中大部分其实是设计内的语义退回。**
   云端回归有 5 张 `cand=0`（含 3 张 food/landscape），我先怀疑是本版新增的"人像时隐藏候选条"过度触发。
   逐张核对后分成两类：多数是 `_buildCompositionCandidates` 在**真实裁切候选少于 2 个**时 `return []`
   （字母 A/B/C 的含义会漂移，此时云端改走语义分析通道而不是联系表）——food/landscape 的照片因为物体保护与
   人物边距把紧裁候选全 veto 掉，正好落进这一支，属设计内行为。**但候选条那条判断也确实过宽**，
   只是它在云端日志里不是主因。**先怀疑 bug、再逐张核对语义，别把"数字难看"整片当成故障，也别因为大部分是
   设计内就放过真 bug。**
   同时把那条隐藏条件本身收窄了：旧条件 `场景含 portrait || aiData.isPerson===true` 在"有用餐者的美食照/
   有远景路人的风景照"上也成立；现在只在"人像/特写场景"或"`isPerson` 且当前根本没裁"时隐藏。
   **实测到的差异（B 组 70 张里唯一的 1 行 diff）**：`night_9.jpg` 是"画面有人物、场景判为 architecture、
   并且已经裁了 `[11,0,0,0]`"的组合 —— 旧条件下它的候选条被收起（日志里 `cands=0`，用户看不到任何可切换方案），
   收窄后 `cands=4`，裁切结果不变。A 组 122 张 0 行差异（那组没有这种组合）。
   也就是说：这条改动找回的是"已裁切但含人物"照片的**切换能力**，不是裁切判断本身。

## 8. 明确不做

生成式外扩/换视角/移主体（与"无后端、不重绘、非商业 License"冲突）；引入 SAM/深度等新端侧模型；
两次串行 VLM 调用；让 VLM 直出自由坐标；对外承诺"AI 美学评分数字"。
