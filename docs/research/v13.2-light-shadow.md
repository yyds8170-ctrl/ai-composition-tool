# v13.2 光影几何与低键滤镜研究

> 日期：2026-10-28
> 样本：内置示例「地下通道」900×1200；`imgs/ls6/ls01`、`ls02`、`ls03`、`ls06` 四张实拍
> 口径：只写可复核的阈值、实测与来源；没有样本支撑的推测明确标注「待校准」
> 边界：本文只做研究记录，不改 `index.html` / `sw.js` / README 或任何代码，也不提交 git

## 1. 为什么做

### 1.1 示例只给出「换画幅 1:1」这种弱建议

内置示例「地下通道」是 900×1200 竖图：大面积暗部、顶部混凝土梁、左上方一束斜光落到地面杂物。它同时具备低键（low-key）、对角光束、明暗切割三个强构图信号，但旧管线给出的最强建议只是「换画幅 1:1」，没有一条候选真正沿着光束收紧。

原因不是没有像素信号，而是信号进不了候选：

1. 旧 `_subjectEvidence` 要求显著主体占比 `sigRatio` 落在 0.02~0.92，或有人物/食物硬证据。地下通道的显著框是整张 `[0,0,1,1]`，`sigRatio≈1`，被判定为「找不到明确主体」；于是只剩画幅候选。
2. v13.2 已在 `index.html:4694` 加了光影兜底：`litRatio≥0.06` 或 `diagRatio≥0.42` 就承认「有内容」；`index.html:4883` 的 `_lightGeometry` 也会生成 `light-tight` / `light-diag` / `light-dark-frame` 三类候选。但这只解决了「能不能裁」，没有解决「裁完配什么滤镜」。
3. 旧滤镜池仍把这类图当「暗但有层次」，`_recommendFilter` 会给 `night` 加分（`mean<90` 加 20），实测把高光剪裁从 0.44% 推到 5.3%；而 `portra` 这类暖调预设一旦进入候选池（人像/美食/日落），又会把黑剪裁从 46.0% 抬到 35.6%。裁切沿着光束，滤镜却把光束打散。

### 1.2 用户反馈「裁切和实际分析不是一个框」

这是 v13.2 P0 的另一个真问题：分析用的是整张原图，预览却把裁切百分比直接套在舞台上。旧舞台固定 4:3 + `object-fit:cover`，导入的竖图会被舞台再裁一次，用户看到的保留框和最终输出自然「完全不是一个」。

代码里已经记录了根因和修法：

- `index.html:2221` 注释：舞台比例改为跟随照片，导入照片用 `contain`；相机仍用 `cover`。
- `index.html:7759` 注释：裁切框必须按「图片在舞台里的真实显示矩形」换算，旧版直接把百分比套在舞台上，竖图只露出中间一条，预览框和最终裁切对不上。

因此 v13.2 的完整目标不是「多一个光束裁切」，而是三件事同框：**分析框 = 预览框 = 输出框**；光束有专属候选；低键图有专属滤镜白名单。本文补的是后两件，第一件已由 P0 的 `contain` + `displayRect` 换算解决。

## 2. 光影几何算法

### 2.1 测量口径

所有数值在 256px 长边的离屏 canvas 上计算，亮度用 Rec.601：

```
L = 0.299R + 0.587G + 0.114B
```

三个硬阈值沿用 `analyzePixels` 的现有口径（`index.html:2669-2670`）：

- 黑剪裁 `shadowClip = #{L < 14} / N`
- 高光剪裁 `highClip = #{L > 243} / N`
- 强亮像素 `lit175 = #{L ≥ 175} / N`（175/255≈0.686）

`mean`、`sd` 在整张 256px 网格上算；「亮区%」则是**包围盒内 `L≥175` 的强亮像素占全图比例**，不是 `L≥μ+0.55σ` 的像素占比。两者混用会把整面被照亮的混凝土墙误当成光束：地下通道的 `μ+0.55σ` 包围盒占全图 59.4%，但强亮只有 8.6%。

本节所有梯度/连通域数值都在 256px 网格上做研究测量；现有 `_lightGeometry` 用的是 16×16 粗网格（`index.html:3131`），阈值可以复用，分辨率不能直接复用——16×16 会把斜光束压成几格，成束判定必须放到更细网格或原图缩略图上做。

### 2.2 亮区包围盒

先算全图均值 `μ` 与标准差 `σ`，阈值取：

```
T = μ + 0.55σ
```

所有 `L≥T` 的像素取 min/max x、y，得到归一化包围盒 `bbox=[x0,y0,x1,y1]`。0.55σ 是经验值：阈值再低，bbox 会包住整面中灰墙；再高，光束会碎成几段。地下通道实测 `T=79.7`，bbox 占全图 59.4%，说明 bbox 只能当「光束搜索容器」，不能直接当裁切框。

候选阶段把 `bbox` 与显著主体框 `sigBox` 求并集，再按面积预算扩到下限（现有 `_lightGeometry` 用 `max(0.06, unionArea*1.28)`，上限 0.72~0.85）。这样光束落点和地面杂物能一起进框，不会只框住最亮的一条。

### 2.3 四向梯度直方图判对角占优

在 256px 网格上做中心差分：

```
gx = L(x+1,y) - L(x-1,y)
gy = L(x,y+1) - L(x,y-1)
m  = |gx| + |gy|
```

忽略 `m < 0.045×255` 的噪声，再按梯度方向分四箱：

| 方向 | 角度范围 |
| --- | --- |
| 水平 h | `abs(angle) < 22.5°` 或 `>157.5°` |
| 垂直 v | `67.5° < abs(angle) < 112.5°` |
| 对角 d45 | 其余且 `angle > 0` |
| 对角 d135 | 其余且 `angle ≤ 0` |

```
diagRatio = (d45 + d135) / (h + v + d45 + d135)
```

`diagRatio ≥ 0.42` 记为「对角占优」，与现有 `_lightGeometry` 的候选门一致（`index.html:4866`、`4917`）。五张图的实测值：

| 图 | diagRatio | 读法 |
| --- | ---: | --- |
| 地下通道 | 0.478 | 对角占优，但墙面纹理稀释了比例 |
| ls01 | 0.464 | 玻璃亭的斜边/光晕占优 |
| ls02 | 0.153 | 水平/垂直木纹占绝对多数，斜光被稀释 |
| ls03 | 0.345 | 窗框以正交为主 |
| ls06 | 0.731 | 蓝色天空与白色结构形成强对角 |

这张表说明：**全图 `diagRatio` 只能判断「画面是否以对角结构为主」，不能判断「局部是否有一束光」**。ls02 全图只有 0.153，但右侧木墙的斜光条仍然成束；所以成束判定必须落到连通域，不能只看全图梯度。

### 2.4 lowKey 判据

lowKey 不是「暗」的同义词，而是「暗部占主导、但亮部仍有明确结构」。五项同时成立：

| 条件 | 门槛 | 理由 |
| --- | --- | --- |
| 均值 | `mean < 95` | 高于 95 更接近中调/高键，暗部不再是结构主体 |
| 层次 | `sd ≥ 45` | 防止「暗而平」的灰雾图；死黑平坦图不配低键滤镜 |
| 亮区 | `0.5% ≤ lit175 ≤ 25%` | 太少没有光束，太多说明是亮墙/高键 |
| 黑剪裁 | `shadowClip ≤ 55%` | 低键允许深黑，但超过 55% 暗部结构已经塌 |
| 高光剪裁 | `highClip ≤ 8%` | 高光已爆的图再加对比只会更糟 |

另外要求 `isPerson=false` 且 `personScore<0.60`：人像有独立的肤色/五官保护链路，不进入这套光影滤镜。

代码现状需要说明：`index.html:4914` 里的 `lowKey` 仍是旧式 `mean<110 && sd>0.11*scale && contrast>0.32`，没有黑/高光剪裁和亮区面积门槛。本文的五项门槛是下一版替换目标，当前代码尚未写入；旧式门槛会把 95~110 的中调图也放进 lowKey，不能直接复用。

### 2.5 光束成束判据

在 `L≥175` 的强亮掩膜上，取 bbox 内的候选连通域（优先最大块；多条平行光带先沿主轴做闭运算合并），计算四项：

| 条件 | 门槛 | 排除的情况 |
| --- | --- | --- |
| 连通域面积 | 5%~30% | 太小是反光点，太大是整面亮墙 |
| 长宽比 | `max(w,h)/min(w,h) ≥ 2.5` | 团状光晕不是光束 |
| 方向 | PCA 主轴与水平夹角 20°~70° | 水平/垂直光带不是斜束 |
| 填充率 | `componentArea / bboxArea ≤ 0.55` | L 形/回字形亮墙不是一束光 |

四项全过才记 `beam=true`；lowKey 且 beam 走「光束」子场景，lowKey 但不成束走「暗调」子场景。两者共用 lowKey 滤镜白名单，但候选裁切的 `light-diag` 只在 beam 或 `diagRatio≥0.42` 时生成。

五张图的成束判断：

- 地下通道：面积 8.6%，闭运算后主束方向约 45°，填充率低于 0.55 → 成束。
- ls01：面积 9.8% 在区间内，但最大连通域长宽比约 1.7、接近团状 → 不成束。
- ls02：面积 6.6%，右侧木墙斜光条经闭运算合并后长宽比高、填充率低 → 成束（按局部连通域，而不是全图 diagRatio）。
- ls03：面积 37.3% > 30% → 直接排除。
- ls06：面积 29.8% 虽在区间内，但亮带以水平/垂直正交结构为主，不是斜束 → 不成束。

| 图 | 尺寸 | mean | sd | 亮区% | 黑剪裁% | 高光剪裁% | diagRatio | 判定 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |

## 3. 滤镜规矩

### 3.1 为什么禁提亮

三条独立证据指向同一个结论：低键图不能靠 `brightness>1.0` 或 `contrast<1.0` 去「救暗部」。

1. **Adobe 的直方图两端是联动的。** Adobe 官方摄影指南的原话是：「If you bring up your shadows to get more detail in them, your highlights are going to get blown out and you'll lose a lot of that detail.」——抬阴影会同时把高光推爆，低键图的高光余量本来就小。
2. **Adobe Stock 把噪点列为最常见伪影。** 其投稿质量要求明确提醒：欠曝/高 ISO 的暗部在提亮后会出现明显颗粒，噪点过多是拒稿的主要原因之一；「reduce noise if necessary — but don't overdo it」也说明后期降噪只能补救，不能当默认动作。
3. **Portra 预设本身就是抬黑位曲线。** 本项目 `portra` 的 CSS 是 `sepia(0.14) saturate(1.12) brightness(1.04) contrast(0.96)`：`brightness 1.04` 抬整体、`contrast 0.96` 压黑位，方向与 low-key「暗部要黑得下去」完全相反。地下通道实测黑剪裁 46.0%→35.6%，不是暗部变好，而是黑位被填灰。

补充：Fujifilm 的 Classic Chrome 官方描述是「Soft color and enhanced shadow contrast for a calm look」，ACROS 是「rich gradation and outstanding sharpness」，NOSTALGIC Neg. 是「Amber tinted highlights and rich shadow tone」。三者共同点是**增强阴影对比/层次，而不是把阴影提亮**；这正是四方案的基调。

### 3.2 四个方案的全强度 CSS

「全强度」指未套对比预算前的模板；落地时 `contrast` 会被 `cMax` 压到不超过 1.18。四个方案都不含 `brightness>1.0`，都不含 `contrast<1.0`。

| 方案 | 全强度 CSS | 适用子场景 | 不适用 |
| --- | --- | --- | --- |
| 保真 | `saturate(1.04) contrast(1.03)` | 彩色光束、暖冷分离明显：夕照穿洞、彩色玻璃、琥珀光+蓝影 | 中性混凝土、无色彩结构 |
| 银盐 | `grayscale(1) contrast(1.18) brightness(0.98)` | 中性硬光、混凝土/金属/楼梯/桥洞/厂房；地下通道这类中性硬光的默认 | 暖木、锈墙、琥珀光束（会丢掉暖色信息） |
| 琥珀 | `sepia(0.16) saturate(1.10) contrast(1.05) brightness(0.99)` | 暖色低键：老墙、木廊、尘土、夕照巷、暖色灯带 | 蓝水、冷玻璃、钢构（会整体发黄） |
| 冷银 | `grayscale(1) sepia(0.12) hue-rotate(180deg) saturate(1.6) contrast(1.12) brightness(0.99)` | 冷色低键：玻璃幕墙、地铁、雨后街道、水面、冷光通道 | 琥珀/暖木光束（会把暖光压成灰蓝） |

注意：现有 `FILTERS.silver` 是 `grayscale(1) contrast(1.3) brightness(0.97)`（`index.html:1736`），contrast 1.3 超出 1.18 上限，不能直接当本文的「银盐」用；本文银盐把 contrast 降到 1.18，给阴影留余量。四个新方案也尚未写入 `FILTERS`，本文给的是下一版白名单，不是现有代码行为。

### 3.3 对比预算：headroom 与 cMax

对比预算同时看高光和阴影，取更紧的一侧：

```
clamp01(x) = min(1, max(0, x))

hHi = clamp01((0.08 - highClip) / 0.08)
hSh = clamp01((0.55 - shadowClip) / 0.30)
headroom = min(hHi, hSh)
cMax = 1 + 0.18 × headroom
cEff = min(cFull, cMax)
```

- `0.08` 和 `0.55` 就是 lowKey 的高光/黑剪裁上限；`0.30` 把「阴影余量充足」定义在 25% 以下，25%~55% 之间线性收紧。
- 系数 `0.18` 让 `cMax` 最大正好等于银盐全强度 1.18；超过 1.18 的对比不再允许。
- `cEff` 只压 `contrast` 一项，`grayscale/sepia/hue-rotate/saturate/brightness` 不动。
- 应用后必须重算 `shadowClip/highClip`：若 `shadowClip>55%` 或 `highClip>8%`，把 `cEff` 每次减 0.02 重试，最多 3 次；仍不过就退回「保真」或原片。预算是事前闸门，不是事后免责。

实测/推算：

| 图 | highClip | shadowClip | hHi | hSh | headroom | cMax | 银盐 cEff | 结果 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 地下通道 | 0.44% | 46.0% | 0.945 | 0.300 | 0.300 | 1.054 | 1.054 | 1.05 实测黑 54.1%、高 0.4%，刚好在 55% 内 |
| ls01 | 0.1% | 16.0% | 0.988 | 1.000 | 0.988 | 1.178 | 1.178 | 1.18 实测黑 30.7%、高 0.1% |
| ls02 | 2.9% | 40.5% | 0.638 | 0.483 | 0.483 | 1.087 | 1.087 | 全强度 1.18 实测黑 62.2%，超限；必须压到公式值 |
| ls03 | 19.0% | 14.4% | 0 | 1.000 | 0 | 1.000 | 1.000 | 连保真 1.03 都已把高光 19.0→19.5、黑 14.4→17.4，只能原片 |

地下通道这一行是整套公式的关键：它的阴影只剩 9 个百分点余量，银盐全强度 1.18 实测会把黑剪裁推到 65.5%；压到 1.05 才回到 54.1%。如果只看高光（0.44% 很安全）就放行 1.18，阴影会先崩。

### 3.4 反向清单

| 禁止项 | 原因 | 现有反例 |
| --- | --- | --- |
| `brightness>1.0` | 抬暗部、推高光；低键图高光余量小 | `night` 1.12：高光 0.44%→5.3% |
| `contrast<1.0` | 压黑位、画面发灰，直接破坏低键结构 | `portra` 0.96：黑剪裁 46.0%→35.6% |
| 人像胶片 | 暖肤色曲线 + 抬黑位，方向与混凝土/光束相反 | `portra`、`ektar`、`portrait-warm`、`portrait-cool` |
| 夜景冷调 | 冷色 cast + 提亮，吃掉琥珀光并爆高光 | `night`、`cool`、`cyber` |
| `sepia≥0.20` | 单色化过强，吃掉暖冷分离 | `warm` 0.2、`sunset` 0.32、`teal` 0.22 |
| 高饱和 | 暗部彩噪被放大，低键最忌塑料感 | `velvia` 1.38、`vivid` 1.5、`160c` 1.26 |
| 柔焦/模糊 | 糊掉光束边缘和墙面纹理 | `soft` `blur(0.5px)`、`fade` contrast 0.88 |

补充一条：`grayscale(1)` 本身不禁止（银盐/冷银就是黑白），但**彩色即主体**的光束不能用纯黑白；判断依据是 `warmRatio≥0.40` 或 `wb≥0.08` 且画面没有 `manmadeScore` 支撑时，优先保真。

## 4. 判定与路由

### 4.1 分支顺序

```
if (isPerson || personScore ≥ 0.60) -> 不进入光影滤镜，走人像链路
if (highClip > 25% || shadowClip > 70% || mean < 35) -> 不自动上滤镜
if (lowKey 五项全过) -> lowKey 分支
else if (silhouette 六项全过) -> silhouette 分支
else -> 不自动上滤镜（保留原片）
```

lowKey 先判，silhouette 后判，避免暗调逆光被两条分支重复路由。两条分支都只允许四方案白名单，不回到 `_recommendFilter` 的通用池。

### 4.2 两条分支的阈值

**lowKey**（五项，全部满足）：

- `mean < 95`
- `sd ≥ 45`
- `0.5% ≤ lit175 ≤ 25%`
- `shadowClip ≤ 55%`
- `highClip ≤ 8%`
- 且 `isPerson=false`、`personScore<0.60`

**silhouette**（六项，全部满足）：

- `mean < 110`
- `sd ≥ 55`
- `shadowClip 20%~65%`
- `highClip 0.5%~25%`
- `lit175 2%~45%`
- `centerLum ≤ 0.65 × borderLum`

其中 `centerLum` 取中央 50%×50% 区域均值，`borderLum` 取四边各 10% 宽条带的均值；这条几何条件用来确认「主体暗、背景亮」，而不是单纯的高反差。现有 `_recommendFilter` 的逆光闸门是 `highClip>12% && shadowClip>35%`（`index.html:3875`），本分支把它扩展成可主动选方案的区间；高光 >25% 或阴影 >65% 时直接拒绝，不做「补救式」滤镜。

本轮没有专门剪影样张，silhouette 的六项是待校准门槛；lowKey 五项已有五张图支撑。

### 4.3 路由表（按优先级，命中即停）

**lowKey 分支**

| 优先级 | 条件 | 方案 | 理由 |
| ---: | --- | --- | --- |
| 1 | `warmRatio ≥ 0.30 && wb ≥ 0.03 && manmadeScore ≥ 0.40` | 琥珀 | 暖色低键，保留灯/木/锈的暖信息 |
| 2 | `waterScore ≥ 0.40 OR wb ≤ -0.05` | 冷银 | 水面/冷光/钢玻璃，冷调单色最稳 |
| 3 | `manmadeScore ≥ 0.45 && abs(wb) ≤ 0.05 && warmRatio < 0.30` | 银盐 | 中性硬光、混凝土几何 |
| 4 | `warmRatio ≥ 0.40 OR wb ≥ 0.08` | 保真 | 色彩就是主体，不能黑白也不能压色 |
| 5 | 其他 | 保真 | 保守兜底；`cMax<1.02` 时退化为原片 |

**silhouette 分支**

| 优先级 | 条件 | 方案 | 理由 |
| ---: | --- | --- | --- |
| 1 | `warmRatio ≥ 0.35 && wb ≥ 0.04` | 琥珀 | 夕照剪影，暖色轮廓是主体 |
| 2 | `waterScore ≥ 0.35 OR wb ≤ -0.05` | 冷银 | 水面/蓝调剪影，冷灰轮廓更干净 |
| 3 | `manmadeScore ≥ 0.50` | 银盐 | 建筑/桥梁剪影，靠形状不靠颜色 |
| 4 | 其他 | 保真 | 保留原有冷暖过渡 |

路由的 4 个信号都用现有 `analyzePixels` 已产出的字段：`waterScore`、`manmadeScore`、`wb`、`warmRatio`（`index.html:3209-3214`），不需要新增像素扫描。`warmRatio` 是暖色像素占比，`wb` 的正负表示暖/冷偏移；两者同时高才是「暖光」，只有 `warmRatio` 高而 `wb` 不偏暖时更像彩色噪点/花色，按保真处理。

## 5. 实测对照

### 5.1 两条反例：portra 抬黑位，night 爆高光

在 256px 长边 canvas 上用 `ctx.filter` 套用现有 CSS，地下通道的实测：

| 滤镜 | CSS | mean | sd | 黑剪裁% | 高光剪裁% |
| --- | --- | ---: | ---: | ---: | ---: |
| 原片 | `none` | 45.3 | 62.6 | 46.0 | 0.44 |
| portra | `sepia(0.14) saturate(1.12) brightness(1.04) contrast(0.96)` | 50.4 | 63.9 | 35.6 | 1.0 |
| night | `brightness(1.12) saturate(0.9) contrast(1.05) hue-rotate(4deg)` | 45.9 | 71.1 | 51.8 | 5.3 |
| 保真 | `saturate(1.04) contrast(1.03)` | 42.6 | — | 51.2 | 0.6 |
| 银盐 1.18 | `grayscale(1) contrast(1.18) brightness(0.98)` | 36.3 | — | 65.5 | 1.8 |
| 银盐 1.05 | `grayscale(1) contrast(1.05) brightness(0.98)` | 40.2 | — | 54.1 | 0.4 |

两条结论：

1. **portra 让黑剪裁 46.0%→35.6%。** 它不是把暗部修好，而是 `brightness 1.04 + contrast 0.96` 把黑位整体抬起来；低键的「黑得下去」被填成灰，光束边缘也变钝。高光从 0.44% 到 1.0% 说明它同时在做整体提亮。
2. **night 让高光剪裁 0.44%→5.3%。** 12 倍的涨幅，而 mean 只从 45.3 到 45.9；提亮主要落在中间调和高光，阴影反而从 46.0% 到 51.8% 更黑。典型的「提亮却更闷」，也是低键图最不能接受的方向。

保真 1.03 和银盐 1.18 的对照说明对比预算不是保守摆设：地下通道的阴影余量只允许到 1.05 左右，1.18 会直接越过 55% 黑剪裁上限。ls03 的高键反例则说明另一侧：高光 19.0% 时 `cMax=1.0`，连 1.03 的保真都会把高光推到 19.5%、黑剪裁从 14.4% 到 17.4%，所以高键图应直接不进入这套滤镜。

### 5.2 为什么不能只扣分，必须白名单硬覆盖

现有 `_recommendFilter` 是「场景池 + 打分」：`night` 对 `mean<90` 加 20 分，`_darkLayered`（`mean≥40 && contrast≥45`）给暗部放行；地下通道正好满足 `mean 45.3 / contrast 62.6`，所以 night 会赢。`portra` 只在人像/美食/日落池里有加分，但它一旦进入候选，同样会把黑位抬高。更关键的是，即使给 night 扣 20 分，night 池里仍有 `cool`/`cyber` 等提亮项；**扣分只能改变排序，不能保证错误滤镜不出现在第一位。**

正确做法是分支级白名单：

```
if (lowKey || silhouette) {
  candidates = [保真, 银盐, 琥珀, 冷银];
  selected = route(candidates);
  // 不进入通用池：portra / ektar / night / cool / cyber / velvia 一律不可选
}
```

白名单之外再加两道保险：

- 反向清单命中即否决（`brightness>1.0`、`contrast<1.0`、`sepia≥0.20`、`sat>0.42` 等）。
- 应用后复算 `shadowClip/highClip`，超出 55%/8% 就降 contrast 或退回原片。

这样「portra 抬黑位」「night 爆高光」不是扣分问题，而是根本不在候选集里；扣分只作为未来新增滤镜的第二道检查，不能替代白名单。

### 6.1 锁 1.1.1 与自托管清单

`model/tasks/README.md` 已锁定 `@mediapipe/tasks-vision@1.1.1`（2026-10-28 下载），7 个文件合计 **32,979,121 字节 ≈ 31.45 MiB（≈32.98 MB）**。按任务口径：

| 项 | 文件 | 字节 | MiB |
| --- | --- | ---: | ---: |
| ESM bundle | `vision_bundle.mjs` | 156,139 | 0.15 |
| WASM SIMD | `wasm/vision_wasm_internal.js` + `.wasm` | 334,128 + 13,519,922 = 13,854,050 | 13.21 |
| WASM no-SIMD | `wasm/vision_wasm_nosimd_internal.js` + `.wasm` | 333,931 + 12,627,509 = 12,961,440 | 12.36 |
| 运行时小计 | 5 个文件 | 26,971,629 | 25.72 |
| 人脸模型 | `models/blaze_face_short_range.tflite` | 229,746 | 0.22 |
| 姿态 lite | `models/pose_landmarker_lite.task` | 5,777,746 | 5.51 |
| 合计 | 7 个文件 | 32,979,121 | 31.45 |

- 「wasm 25.7 MiB」= 4 个 wasm 文件（26,815,490 B = 25.57 MiB）+ `vision_bundle.mjs`（0.15 MiB），合计 25.72 MiB。
- 「face 0.22 MiB」「pose_lite 5.5 MiB」与上表一致；按任务口径就是：**wasm 25.7 MiB + face 0.22 MiB + pose_lite 5.5 MiB ≈ 33 MB**（十进制），折合 31.45 MiB。
- 每个文件的 sha256 在 `model/tasks/README.md`，迁移时先校验再加载；Apache 2.0，保留 `LICENSE` 与 README。
- 不要把 33 MB 加进 `sw.js` 的 `CORE` 预缓存数组；当前 `sw.js` 的 cache-first 分支已经会在首次使用时写入缓存。首次开启「真 AI 精修」后再预热，避免首屏被 33 MB 拖住。

### 6.2 加载与 delegate

```js
const vision = await FilesetResolver.forVisionTasks('./model/tasks/wasm');
const face = await FaceDetector.createFromOptions(vision, {
  baseOptions: { modelAssetPath: './model/tasks/models/blaze_face_short_range.tflite', delegate: 'CPU' },
  runningMode: 'IMAGE',
});
```

- `delegate: 'CPU'` 必须显式写死。1.1.1 的 bundle 默认就是 CPU（`delegate=t.baseOptions?.delegate??"CPU"`），但显式写可以防止未来升级改默认。
- iOS Safari 的 GPU delegate 有未修 issue #6142（2025-11-09，open）：ImageSegmenter 在 iOS Safari + GPU 下类别错乱，CPU 正常；本项目的 face/pose 迁移不应在 iOS 上默认 GPU。
- GPU delegate 还有 #6352（2026-08-31，open）：连续 `segmentForVideo` 75 分钟，Emscripten GL 句柄表（framebuffers/textures/syncs）各涨到 11.19 MB，RSS 约 +1.2 MB/min；issue 给出的缓解办法是每 5 分钟重建实例并 `close()` 旧实例。CPU 不经过 GL 表，默认 CPU 同时避开 #6142 和 #6352。
- GPU 只能作为 opt-in：单独 feature flag，先检测平台，iOS 禁用；开启后每 5 分钟重建 + close，并监控内存。

### 6.3 `boundingBox` 是像素，`keypoints` 是归一化

这是迁移最容易写错的一处：

- `Detection.boundingBox` 是**输入图像的像素坐标**：`originX/originY/width/height`。官方 Face Detector Web 示例直接给出 `origin_x: 126, origin_y: 100, width: 463, height: 463` 这类值，不能再乘图片宽高。
- `Detection.keypoints` 的 `x/y` 是**归一化 0~1**；Pose Landmarker 的 `landmarks` 也是归一化，`worldLandmarks` 才是米制 3D。
- 转换：

```js
const box = {
  x: det.boundingBox.originX,          // 已是像素
  y: det.boundingBox.originY,
  w: det.boundingBox.width,
  h: det.boundingBox.height,
};
const kp = {
  x: det.keypoints[0].x * inputWidth,  // 归一化 → 像素
  y: det.keypoints[0].y * inputHeight,
};
```

- 如果输入是缩小后的 canvas（例如 640px），所有坐标都属于 640px 空间；映射回原图要再乘 `originalWidth/640`，不能把 bbox 和 keypoints 分别用不同比例。
- 建议在适配层入口统一转成项目内部的归一化 0~1 坐标，只转一次；不要在业务层混用「bbox 像素 + keypoint 归一化」。现有 `info.bbox` 约定是归一化（`index.html:3313` 附近），迁移时保持这个契约。

### 6.4 `close()` 必须调

- 任务实例（`FaceDetector` / `PoseLandmarker` / `ImageSegmenter`）和分割 mask 结果都有 `close()`；至少任务实例必须在模式切换、图片替换、`pagehide` 时关闭。
- 用 `try/finally` 保证异常路径也关；不要每帧 `createFromOptions`，一个任务一个实例，复用到页面卸载。
- #6352 的复现数据说明不关的代价：75 分钟 GL 表各 11.19 MB、RSS 持续上涨；issue 的缓解方案就是「recreate + close old」。即使 CPU 没有 GL 表，WASM 堆也需要 `close()` 释放。
- 关闭后把引用置空，避免旧实例被闭包持有；重新开启时重新 `FilesetResolver` + `createFromOptions`。

### 6.5 legacy 与 tasks 混用是已知 abort 成因

#5495（2024-06-20，closed）的原始描述：同一页面用 `mediapipe@pose`（legacy）做姿态、同时用 `@mediapipe/tasks-vision` 做手部，出现 abort，日志里是 `module.arguments` 被替换成 plain arguments，偶尔 memory out of bounds。原因是两套 Emscripten 运行时共享全局 `Module`。

本仓库正好同时存在两套资源：

- `model/mediapipe/face_detection`、`model/mediapipe/pose`、`model/mediapipe/selfie_segmentation` 是 legacy Solutions；
- `model/tasks/` 是 Tasks Vision 1.1.1。

迁移时必须按页面/功能整体切换，不能在同一页同时 import 两套。灰度方案只能是「旧页面继续 legacy / 新页面只用 tasks」，或者把其中一套放进独立 worker/iframe 隔离；不能假设「只加载一个模型文件」就不会冲突，运行时全局仍然会撞。

另外，v13.2 代码里已记录：1×1 探针帧会让部分 build 的 `detections` 缺失，触发 wasm abort（`index.html:11294`、`11329`）；迁移后的健康检查用 64×64 真实画布帧，不要用 1×1。

### 6.6 迁移顺序与验收

1. **P0 冻结**：1.1.1 + sha256 + Apache LICENSE；确认 7 个文件都在仓库，不依赖 CDN。
2. **P1 人脸框**：先只迁 FaceDetector，bbox 像素 → 内部归一化；用五张图对比旧 legacy 的人脸框，IoU 不低于 0.95。
3. **P2 姿态 lite**：迁 PoseLandmarker Lite，保留 `pose_landmarker_lite.task`；确认 `keypoints` 归一化、`worldLandmarks` 不用于 2D 裁切。
4. **P3 去 legacy**：同一页面移除 legacy import；用 #5495 的复现路径做回归（legacy pose + tasks 同页必须不再出现）。
5. **P4 GPU opt-in**：仅非 iOS、显式开关；每 5 分钟重建 + close，监控 #6352 的内存曲线。

验收口径：

- 五张样本的 `crop` / `filter` 方案与本文表格一致；地下通道进入 lowKey + 光束，ls03/ls06 不进入。
- iOS Safari 用 CPU 连续分析 30 分钟无 abort、无类别错乱；`close()` 调用计数 = 实例创建计数。
- 页面卸载后 WASM 堆不持续增长；30 分钟后 RSS 斜率接近 0。
- 日志中不出现 `Module.arguments`、`memory out of bounds`、`null detections`。
- 首屏不因为 33 MB 资源变慢；首次开启真 AI 后才按需加载并缓存。
